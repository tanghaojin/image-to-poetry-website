# 古典诗词线上接口调研

调研日期：2026-09-12

## 目标

为“见景寻诗”的图片理解结果寻找真实古典诗词，重点检查：

1. 浏览器能否直接跨域调用；
2. 能否按景物、季节、天气、时段、意境检索；
3. 是否返回题名、作者、朝代、正文；
4. 数据是否适合作为最终展示依据；
5. 免费层、鉴权、稳定性和前端直连条件。

## 结论

目前调研到的免费线上接口中，**诗泉是最适合做候选召回的接口，但不适合直接作为最终权威数据源**。它支持全文检索、无需密钥、允许浏览器跨域请求，数据量也最大；实测同时发现朝代误标、重复记录、异文和排序不稳定。

“今日诗词”接口的数据结构较完整、可直接在浏览器使用，但它主要根据访问者的位置、天气、时间等信息随机推荐，不能提交图片识别出的自定义意境，因此更适合作为首页随机诗句或兜底展示。

产品要求“只做真实古典诗词”，推荐采用：

> 本地校验过的名篇库作为事实来源 + 线上接口扩大候选召回 + 本地确定性校验与排序。

首版即使保持纯前端，也可以把 500–2000 首已校验诗词打包为静态 JSON，并建立轻量倒排索引；线上接口只补充候选，不让未经校验的作者、朝代和正文直接进入作品页。

## 接口对比

| 数据源 | 自定义检索 | 完整诗词信息 | 浏览器直连 | 实测结果 | 建议用途 |
|---|---|---:|---:|---|---|
| 诗泉 | 支持全文、作者、朝代、类型筛选 | 支持 | 支持，CORS `*` | 可用，但有朝代误标、重复和异文 | 候选召回 |
| 今日诗词 V1 | 仅随机或固定分类 | 只有诗句、题名、作者、分类，缺朝代与全文 | 支持，CORS `*` | 可用 | 首页随机诗句 |
| 今日诗词 V2 | 不支持提交自定义图片标签 | 支持题名、朝代、作者、全文 | 支持指定 Origin，需 Token | 可用；匹配标签来自用户环境 | 随机兜底，不做主匹配 |
| chinese-poetry | 本身不是在线查询 API | 静态数据较全 | 需自行托管/打包 | 数据量大，也存在公开校对问题 | 构建候选库后人工/程序校验 |

## 1. 诗泉 chinese-poetry-api

- 项目：<https://github.com/palemoky/chinese-poetry-api>
- 在线服务：<https://poetry.palemoky.com/>
- 数据源：`chinese-poetry`
- 许可证：GPL-3.0
- 文档声明约 40 万首；在线统计实测为 371,313 首、13,577 位作者。
- 支持 REST、GraphQL、全文检索、朝代/作者/类型筛选、简繁转换。

### 在线路由实测

线上实例的可用路由与仓库 README 中的自部署示例不完全一致：

- `GET /health`
- `GET /api/stats`
- `GET /api/search?q=关键词`
- `GET /api/poems/random`

线上 `/api/v1/*` 实测为 404，因此接入时应以在线首页列出的路由为准。

### 检索特性

- 查询词至少 3 个字符；`孤舟`返回 400。
- `寒江孤舟`、`清寂悠远`、`冬日清晨`均没有命中，说明它不是语义搜索。
- `独钓寒江雪`能召回柳宗元《江雪》，但经典版本并未排在第一位，结果还包含重复记录和“万径/万迳”等异文。
- 抽象意境不能直接作为查询词，需要先把识别结果转换为具体诗歌意象词组，例如“孤舟寒江”“落日江水”“桃花春山”。

### 数据质量风险

实测结果中，杨万里、韩元吉、周孚、姚勉、刘辰翁、舒岳祥等作者被标为“唐”，存在明显朝代误标。项目问题列表也已有“数据库重复情况严重”“搜索结果多处错别字”等反馈。上游 `chinese-poetry` 数据集同样存在公开校对问题。

**判断：** API 工程能力和浏览器兼容性良好，适合扩大候选范围；最终展示前必须经过本地标准库校验、去重和异文选择。

## 2. 今日诗词

- 文档：<https://www.jinrishici.com/doc/>
- V1 仓库：<https://github.com/xenv/gushici>

### V1

`https://v1.jinrishici.com/all.json` 实测返回 200，并允许跨域。也支持类似 `shuqing/sixiang.json`、`shuqing/libie.json` 的固定分类。

局限：

- 返回的是随机一句，不是搜索结果；
- 没有朝代和完整原文；
- 分类粒度固定，不能提交图片的主体、天气、时间和意境组合。

### V2

V2 需要先获取并持久化客户端 Token，再调用 `/sentence`。实测能返回诗句、完整出处、朝代、作者、全文、热度及匹配标签。

它的 `matchTags` 来自当前访问者 IP、地理位置、天气、时间和季节，并非上传图片内容；响应中还会包含用户网络信息。对本项目而言，这种匹配逻辑可能把“用户所在地天气”误当成“照片意境”。

**判断：** 可用于首页每日诗句或主流程失败时的随机兜底，不进入基于图片的主要匹配链路。

## 3. chinese-poetry 数据集

- 仓库：<https://github.com/chinese-poetry/chinese-poetry>

它是大型静态数据集，不是托管查询 API，覆盖唐诗、宋诗、宋词等。可以在构建阶段下载、筛选和生成前端静态索引，但需要自行处理：

- 重复记录；
- 简繁、标点和异体字归一化；
- 作者与朝代校验；
- 名篇优先级；
- 公开 issue 中已报告的错字及异常记录。

## 推荐匹配链路

### 首版方案

1. **图片理解结果标准化**：保留主体、季节、时段、天气、唯一最高可信意境和画面摘要。
2. **生成检索意象**：规则生成 3–5 组至少 3 字的具体短语，避免直接搜索抽象情绪。
3. **本地名篇库先召回**：用标签、标题、正文倒排索引召回候选。
4. **诗泉补召回**：只在本地候选不足时请求 `/api/search`，结果先去重、规范化。
5. **事实校验**：仅保留能在本地标准库确认题名、作者、朝代和正文的记录。
6. **排序**：综合景物、季节、天气、时段、意境、名篇权重评分，固定输出最高分一首。
7. **无可靠候选时**：扩大本地标签范围重新排序，不展示未经校验的在线结果。

### 建议评分

```text
总分 = 0.32 × 景物匹配
     + 0.18 × 季节匹配
     + 0.10 × 天气匹配
     + 0.08 × 时段匹配
     + 0.22 × 意境匹配
     + 0.10 × 名篇权重
```

硬性条件：

- 题名、作者、朝代、正文均已校验；
- 不使用模型新写诗句；
- 不让模型改写原文；
- 同一作品异文只保留项目选定的标准版本；
- 最终只输出得分最高的一首。

## 下一步实施建议

先做一个 30–50 首的小型校验语料切片，覆盖当前三张示例图常见的“落日江山、寒江孤舟、春日桃花”等场景，完成：

1. 诗词数据结构与标签规范；
2. 本地召回和评分函数；
3. 诗泉候选接口适配器；
4. 去重、异文和事实校验门禁；
5. 三张示例图的固定回归测试。

验证通过后再扩充到 500–2000 首，避免先引入大数据集后集中处理数据质量问题。
